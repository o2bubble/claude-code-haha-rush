# AI_NOTES — config-export（配置与资料导出）

把本机 Claude 个人资料 + GUI 配置扫描分类、勾选打包成 `.tar.gz`。
贡献：1 个面板（`config-export-panel`）+ 1 个进程（`config-export-server`）+ 2 个 MCP 工具。

## 给 AI 用：什么时候调

用户说「帮我把配置导出来」「我要换电脑」「备份一下我的设置」时：

1. `list_exportable` —— 先看有什么、多大、哪些敏感
2. 把清单**按人话**转述给用户，特别指出：
   - **会话历史**默认不含（几百 MB + 全部对话明文），要的话需明确说
   - 哪些分类标了敏感
3. `export_profile` —— 传 `categories`。不传 = 用默认选择
4. 把返回的 `path` 告诉用户

> ⚠️ **不要替用户勾选敏感分类**（`sensitive: true`）—— 先问。

## 安全边界（不可绕过）

**凭据永不进包**，硬编码在 `export-server.cjs` 的 `NEVER_EXPORT`：
`~/.claude/.credentials.json`、`plugin-signing.key`、`.env.active`、`.env.profiles`。

即使调用方在 `categories` 里点名相关分类，这些文件也会在遍历时被跳过
（`isNeverExport()`）。**settings.json 的 `env` 段永远剥离**，并在
`manifest.redactions` 留痕。

如果用户问「为什么导出的设置里没有我的 API key」—— 这是**预期行为**，如实解释。

## 自定义项（custom items）—— 开放世界扩展点

有些东西插件**无法枚举**：用户自己的一套迁移方案（手册 + 脚本 + 私有数据）、
私有数据库、云服务、加密文件。它们的**逻辑只存在于用户和自己的 AI 之间**。

**插件不解析它们的内容**，只做三件事：

| 做 | 不做 |
|---|---|
| ① 记录方案（入口文档 / 导入指引 / 验证方式）；`includeData:true` 时才打包目录 | ❌ 不解析、不改写里面的任何文件 |
| ② 在 `manifest.customItems` 记录它是什么、入口文档、导入/验证指引 | ❌ 不判断该不该覆盖 |
| ③ **自动算出与内置分类的重叠**，写进 `IMPORT_GUIDE.md` | ❌ 不执行用户的方案 |

### 关键设计：重叠必须"先问用户"

用你的场景说：用户之前自建过一套 `X 盘两机同步`（`~/.claude` 的技能/记忆/历史全走它）。
这次又用本插件导出，**同一批文件会出现在两处**（内置分类 + 自定义项）。

导入端 AI 若不加判断地两边都恢复 → 可能覆盖用户精心维护的旧方案。
所以 `IMPORT_GUIDE.md` 里对每个重叠项都写了：

> ⚠️ 先问用户「这套方案之前是不是已经做过？」
> · 已做过 → 只导入增量，或问用户是否要用包里的版本更新
> · 没做过 → 按 entryDoc 正常执行
> · **绝不静默覆盖**

**插件只提供事实（哪些文件重叠了、重叠多少），判断权交给 AI 与用户。**

### 自定义项**不走凭据黑名单**

`NEVER_EXPORT` 只作用于**内置采集范围**。用户自定义目录里就算有 `profile.env`，
也**原样带走** —— 那是用户自己方案的组成部分，插件无权替他们删。

### 包内 `IMPORT_GUIDE.md`

导出时自动生成（`formatVersion: 2`）。它是**给导入端 AI 读的流程框架**：
内置条目按 `restore.mode` 分组 → 自定义项逐个给入口/指引/重叠提示 → 验证与报告。

### 🔴 备份有效性门控：`RESTORE_REHEARSAL.md`

**导出成功 ≠ 备份有效。** 用户要的是「这份备份在新机器上**真的能还原**」。

包内除 `IMPORT_GUIDE.md` 外还有 **`RESTORE_REHEARSAL.md`**，分两段：

**一、自动检查（导出端已跑完，结果写进文档）**

| 检查 | 抓什么 |
|---|---|
| 内置条目文件齐全 | 包内路径缺失 |
| 每个文件都有 sha256 | 读失败（空 hash） |
| 没有零字节文件 | 源文件当时是空的 / 读失败 |
| **自定义项入口文档存在** | **最常见的「备份了但恢复不了」** —— 文档指向的文件根本不在 |
| 自定义项数据是否在包内 | 提醒 AI：哪些方案只记了说明 |
| 凭据处理已记录 | 恢复后需用户重配什么 |

**任一条 ❌ → 文档顶部直接写「这份备份不可靠，先修复再谈恢复」**，
导出返回值的 `autoChecks` 也会带着失败项。

**二、必须推演的问题（逐条回答，不能跳过）**

1. 这份备份在**全新机器**上能恢复吗？（含 `manual` 模式的冲突策略）
2. 路径在新机器上还成立吗？（写死的绝对路径 / 用户名 / 盘符）
3. **每个自定义项**在新机器上怎么恢复到可用状态？
   —— 关键是判断：那份文档是**只描述了现状**，还是**真的写了怎么恢复**
4. 有没有「文档没提、不带就恢复不了」的东西？（依赖包 / key / 插件 / 外部数据）
5. 反向验证：这次备份**失败**会丢什么？哪些是唯一副本？

**结论必须报三件事**：能不能用 / 有哪些坑 / 建议补什么。

> ⚠️ 导出返回带 `guideHint`，明确写着 **「推演通过前，不要告诉用户『备份已完成』」**。
> 不要跳过。

## 故障模式

### 1. 面板显示「未拿到插件进程端口」

`port` 参数缺失 → 进程没起来。查：
- `plugin_list` 看 `config-export` 的 processes 状态（`error` = 启动即退）
- 依赖 `nodejs` 是否已装且就绪（本插件 `dependencies: ["nodejs"]`）
- 进程 stderr 在 GUI 日志里（`[plugin:config-export-server stderr]`）

### 2. 导出报 `tar failed`

Windows 上 `tar` 必须带 `--force-local` —— 否则 `C:\...` 会被 GNU tar 当成
远程主机名（`tar (child): Cannot connect to C: resolve failed`）。
代码里已带；若见到这个错，说明跑的是旧版本。

GNU tar 对「文件在读取期间变化」返回码 1 并打警告，**包其实是好的** ——
代码只把 `>=2` 当错误。

### 3. 导出的包里没有某个分类

该分类 `collect()` 返回空 = 本机确实没有那些文件。用 `list_exportable` 的
`fileCount: 0` 确认。常见：新机器还没有 `notes/`、`plans/`。

### 4. 工作区 slug 对不上记忆目录

slug 必须与主仓 `src/utils/sessionStoragePortable.ts:311` 的 `sanitizePath`
完全一致（非字母数字 → `-`，超长截断 + hash）。**不要自创算法** —— 差一个字符
工作区数据就和它的记忆目录对不上号。

### 5. 用户取消保存对话框

`export-save-result` 回 `path: null` → 面板自动降级为「存到下载文件夹」。
**这是预期行为**，不是失败。

## 日志与状态位置

- 安装目录：`%APPDATA%/com.claudecode.gui/plugins/config-export/`
- 进程 id：`plugin:config-export:config-export-server`（stdout 打印 `PLUGIN_PORT=`）
- 日志：GUI 日志里 `[plugin:config-export-server stderr]`
- 端口自查：`curl http://127.0.0.1:<port>/api/health` → `{ok, workspace}`

## 配置依赖

- **dependencies: `nodejs`** —— 进程用 `node` 跑 `export-server.cjs`。缺了拒绝安装
- installType: `standard`
- platforms: `["windows"]`（打包用系统 `tar` + Windows 路径语义；其它平台需另验）
- 无 `contributes.skills`（本插件不需要 AI 技能）

## 与宿主的能力协商

面板从 iframe URL 的 `caps=` 读宿主能力：

| 有 `export-save` | 行为 |
|---|---|
| 有 | 点导出 → 宿主弹系统保存框（`kind:"export-save"` 上行）|
| 无 | 直接存 `~/Downloads/claude-profile-export-<ts>.tar.gz`，完成后请求宿主打开该目录 |

**这样旧版 GUI 装新插件也能用**，只是少了选路径那一步。

### 6. 导出报 `tar failed ... Unexpected EOF in archive`

打包时某个文件**正在被写入**（会话日志、数据库 WAL）。常见于把整个
`~/.claude` 当自定义项打包。

代码已做**完整性校验**：tar 报错后会再跑一次 `tar -tzf` 复核，能完整列出才算成功。
若确实失败，建议：
- 导出前**关闭 GUI / 其它 CC 实例**（减少写入）
- 或只选需要的分类，别整个目录打包

⚠️ **不要退回"产物非空即成功"** —— `Unexpected EOF` 会留下**半截包**（size > 0），
那种逻辑会把损坏的包当成功交给用户。

### 7. 自定义项导出后 AI 不知道从哪读起

`entryDoc` 没填。检查 `manifest.customItems[].entryDoc` —— 为空时 GUIDE 会写
「⚠️ 未指定入口文档 —— 需要用户告诉你从哪个文件读起」。补上再导一次。

## 恢复侧：AI 全程参与，不是照表拷文件

🔴 **恢复不是「解压了就完事」。** 新机器上可能已经有：装好的插件、跑过几个会话、
改过的设置、自己的记忆。按固定模式覆盖 = 毁掉用户在新机器上已有的东西。

`IMPORT_GUIDE.md` 里的 **「第 0 步：先评估新机器现状（不能跳过）」** 是硬要求：

**① 先查（别猜）**

| 查什么 | 为什么 |
|---|---|
| `~/.claude/` 有什么 | 全新 vs 已用过，策略完全不同 |
| 已有哪些会话 | **同一会话两台机器进度可能不同** |
| 已装哪些插件 | 与 `installedPlugins` 比对 |
| 记忆/笔记/桌面有内容吗 | `manual` 模式，冲突要问用户 |
| 用户名 / 盘符 | 决定路径要不要改写 |

**② 再出方案，用户确认后才动手**

**③ 冲突按内容类型分别处理**（不用一条规则套全部）

| 内容 | 建议方向 |
|---|---|
| 会话 `.jsonl` | **按 uuid 合并**（不是覆盖/追加/取长的） |
| `settings.json` | 按键合并，保留新机器已有值 |
| `CLAUDE.md` | 看差异，去重后追加或让用户挑 |
| 记忆 / `data.db` | **必须问用户**（人工沉淀 / 二进制无法合并） |
| 插件 | 保持新机器版本，只补缺的 |

**④ `overwrite` ≠ 闭眼覆盖** —— 它只说明"没有合并语义"，目标已存在时仍要问用户。

**⑤ 破坏性操作前先备份现状，逐步执行可回退。**

### 自定义项：完全靠 AI 驱动

没有固定模式可套。流程是：**读 entryDoc → 摸清现状 → 制定方案 → 用户确认 → 执行 → 验证**。

⚠️ **用户文档 ≠ 一定能执行**：硬编码路径（`C:\Users\吴亚飞`）、依赖的软件、需要 GUI 操作的步骤
—— 遇到这些**如实告诉用户做不到**，不要绕过、不要自己发明替代方案。

### 会话合并专项

导了会话时，`IMPORT_GUIDE.md` 会附一整章「按 uuid 去重合并」的做法，并明确禁止：
❌ 直接覆盖（丢进度） ❌ 简单追加 ❌ 按行数取长的（可能分叉） ❌ 不备份就改

## 包内自带工具 `tools/restore-tools.cjs`

**别临场写脚本** —— 恢复期的固定套路都固化在包里了，直接调用：

| 命令 | 作用 |
|---|---|
| `list <包>` | 包里有什么（分类/文件数/大小/自定义项/下一步建议） |
| `verify <包>` | 包完整性（逐个 sha256 比对） |
| `compare <包> --dest <dir>` | 包内容 vs 新机器现状（missing / different / exists / unresolvable） |
| `rate <包> --dest <dir>` | **恢复率**（见下） |
| `extract <包> --dest <dir>` | 解包（只解，不放到目标位置） |
| `session-diff <a> <b>` | 两个会话文件差异（按 uuid，能识别真冲突） |
| `session-merge <a> <b> -o <out>` | 按 uuid 合并（自动备份；有真冲突时**拒绝合并**） |
| `json-merge <a> <b>` | 两个 JSON 按键合并的**预览**（不写盘） |

全部输出 JSON；出错时 exit code ≠ 0 且 stdout 也有 `{ok:false,error}`。

### 🔴 恢复率：报**两个**数，不要合成一个

| 指标 | 含义 |
|---|---|
| **自动验证通过率** | 能自动验的里面验过了多少 |
| **整体覆盖率** | 算上无法自动验证的之后，覆盖了多少 |

按 `restore.mode` 分三级：

| 级别 | 对应 mode | 判据 |
|---|---|---|
| **精确** | `overwrite` | **sha256 逐字节一致** |
| **部分** | `merge` / `append` | 合并后内容必然不同，只能验"存在" |
| **无法验证** | `manual` | 记忆 / `data.db` / 自定义项 —— **没有客观标准** |

**为什么不能合成一个数**：`manual` 类的文件（记忆、桌面数据库）没人能自动判断
"合并得对不对"。把它们算进百分比就是**假精确**。合成一个数会掩盖
「55 个记忆文件根本没验」这个事实。

报告示例：

```
自动验证通过率 85%（17/20）—— 能验的都验过了
整体覆盖率   60%（17/28）—— 另有 8 项需要你确认
  · 记忆 6 项（无法自动比对）
  · 桌面数据库 1 项（二进制）
  · 自定义项 X盘同步（需按你的文档验证）
```

**别只说「恢复完成」** —— 要说清楚哪部分验过、哪部分没验、为什么。

### Windows 上 tar 的两个坑（写工具的教训）

1. **不加 `--force-local`** → `C:\...` 被当远程主机名（`Cannot connect to C:`）
2. **加了它 + `-C 绝对路径`** → `C:` 被当盘符语法转义成 `C\:\...` → 路径不存在

最终做法：**先把包 copy 到目标目录，再以纯文件名解包**（cwd=目标目录，全程无绝对路径参与 tar）。

## 导出侧：自定义项「文档自检」（`/api/audit-custom`）

🔴 **用户的方案文档自己可能就不全。** 真实案例：`00_迁移总览.md` 里写了
12 个文件名（`01_台式机同步到X.bat`、`06_修复用户名.py`…），但那个目录里
**只有这一个 .md**。直接导出 = 备份残缺，而且要等换机器才发现。

**导出前**面板会调 `/api/audit-custom` 做交叉核对：

```
文档里提到的文件名（正则抽 .bat/.py/.md/.txt/.json…）
        −
目录里实际存在的文件名（递归收集 basename）
        =
缺失项
```

结果按严重度分级：

| 级别 | 情况 | 是否阻断导出 |
|---|---|---|
| 🔴 `high` | 入口文档不存在 / 文档引用**缺失过半** | **弹确认框**（用户可坚持导出）|
| 🟡 `medium` | 有缺失但不到一半 | 提示 |
| ⚪ `low` | 没给 `importPrompt` / `verifyPrompt` | 只提示 |
| ℹ️ `info` | 数据不在包里 | 只提示 |

**用户确认「我知道不完整」后仍可导出** —— 但缺失清单会写进
`manifest.customAudit` 和 `IMPORT_GUIDE.md`，恢复端能看到「这份文档本身残缺」。

**只做文件名级匹配**（不做路径推断 —— 那会误报）。命中不了的交给人判断。

### 给 AI 的用法

用户说「把我的迁移方案也导出去」时：

1. 调 `export_profile` 前，可以先单独问一句这条路有没有缺失
2. 返回的 `autoChecks` 里有一项 **「自定义项文档引用的文件都在」**，
   失败时把缺失清单如实告诉用户，问他：
   - 那些文件是不是**在别的位置**？（用户方案的脚本常散落多处）
   - 还是**根本没备份过**？
   - 或者只是文档里的**举例名**？
3. 用户说「就这些」→ 继续导出；说「我去补」→ 等补齐再导

## 恢复入口：**由插件本身提供**（不靠用户记得说什么）

新机器上的 AI 拿到一个 `.tar.gz` **不会自己知道**它有配套恢复协议。
所以插件面板自带「**从备份恢复**」区块：

```
[选择备份包…] → 读包（/api/inspect-package）→ 显示摘要 → [交给 AI 开始恢复]
```

点「交给 AI 开始恢复」会通过 uplink `chat-prompt` 把一段**完整的恢复提示词**
填进聊天输入框，**用户按发送**才执行（用户掌握启动权）。

提示词里已经写死了流程：评估现状 → 出方案 → 用户确认 → 冲突按类型处理 → 报两个恢复率。

### MCP 工具（导出/恢复两端 AI 都能用）

| 工具 | 什么时候用 |
|---|---|
| `list_exportable` | 用户要导出，先看有什么 |
| `audit_custom_item` | 用户要把**自己的方案**加进来，**先体检它** |
| `export_profile` | 执行导出（可带 customItems） |
| `inspect_package` | **用户给你一个备份包要恢复 → 先调这个** |

### ⚠️ `ok` vs `clean`（audit_custom_item）

- `ok: true` = **这次调用成功了**
- `clean: true` = **这份方案本身没问题**

两者独立。`ok:true, clean:false` 表示"查出来有问题"（不是工具坏了）。

### 导出成功后 AI 该做什么

`export_profile` 的返回里有：

- `bundledFiles` —— 包里有哪些文档/工具
- `toolsHint` —— **"用包内工具，不要临时写脚本"**
- `nextActions` —— 三步：推演 → 报结论 → 用户确认后才说"可用"
- `recommendedImportPrompt` —— 可原样转述给用户的恢复提示词

**别只看 `ok:true` 就说"备份完成"** —— 还有 `rehearsalRequired` 的门控。
