# 快捷键系统

## 定位与边界

**只管「应用级快捷键」** —— 无论在哪个面板都生效的那些。

**不纳入**：对话框里的 `Esc`/`Enter`、列表上下键、`Tab` 导航等**局部交互键**。
它们的语义强依赖上下文（同一个 `Enter` 在对话框和输入框里行为不同），纳入会让
「冲突检测」失去意义。这些键继续留在各自组件里。

## 三种条目（决定能否被用户修改）

| 类型 | 例子 | 可改 | 说明 |
|---|---|---|---|
| **全局** | 命令面板（`F1`/`Ctrl+Shift+P`）、硬刷新（`Ctrl+R`） | ✅ | 任何地方生效 |
| **命令型** | 面板切换、打开设置 | ✅ | 走 `commandRegistry.execute(commandId)` |
| **上下文型** | 笔记 `Ctrl+N/K/E`、文件树 `Ctrl+C/V` | ❌ **只读展示** | 依赖焦点/挂载/选中状态。改了键也可能因条件不满足而不生效，让用户改是误导 |

上下文型在表里标 `contextual: true`，设置面板用虚线框展示、不可点。

## 文件

| 文件 | 职责 |
|---|---|
| `services/shortcuts.ts` | **唯一真相源**：类型、键位解析/格式化、默认表、冲突检测、合并逻辑 |
| `services/shortcutDispatcher.ts` | 全局 keydown 分发器（单监听）+ `shouldDispatch` 上下文判定 + `isMacPlatform` |
| `components/chat/ShortcutsPanel.tsx` | 设置 → 快捷键 的管理界面 |
| `components/chat/settingsStyles.ts` | 共享样式（从 SettingsPanel 抽出，避免循环引用） |

## 键位格式

**规范化字符串**：小写、修饰键顺序固定 `mod → ctrl → alt → shift → 键名`。

```
"mod+shift+p"   "f1"   "mod+,"   "mod+alt+b"
```

**`mod` 是必需的抽象** —— 它表示「Ctrl（Win/Linux）或 Cmd（mac）」，让「切换左面板」
这类概念在两平台用**同一份配置**表达。平台差异在**渲染时**解决（`displayKeys`）：

```
Windows:  Ctrl+Shift+P
mac:      ⇧⌘P
```

用户手写的乱序（`"shift+mod+p"`）在读取时**归一化**，所以比较与冲突检测都不会漏。

**`+` 键名写作 `plus`**：`+` 是分隔符，直接拼会得到 `"mod++"`，再解析时按 `+`
切分会把键名当空片段丢掉（往返有损）。统一表示为 `"mod+plus"`，手写也接受 `plus`。

**设置面板的录制器只产出 `mod`，不产出 `ctrl`** —— 这是**刻意的**：`mod` 已经是
"Ctrl-or-Cmd"这个跨平台抽象，让用户在 Windows 上录出 `ctrl+` 前缀只会造出一个
mac 上不生效的绑定。`ctrl` 前缀留给**手写配置**（`formatKeys`/`parseKeys` 都支持），
用于"确实要区分 Ctrl 与 Cmd"的罕见场景。

## 冲突策略：软冲突

**允许**绑到同一个键 —— 保存时不阻止，但：
- 设置面板顶部汇总提示「N 组键位冲突」
- 冲突的键位用警示色边框
- 提示文案写明「按列表顺序，靠前者优先」

**运行时优先级 = 表内顺序**（`DEFAULT_SHORTCUTS` 的数组顺序），**不是"后注册赢"**
—— 注册顺序受组件挂载时机影响（谁先渲染谁先注册），用户改个布局就可能改变谁赢，
是不确定的。表内顺序则**用户可见、可调整**。

上下文型条目**不参与冲突检测**：它们的生效条件互斥（笔记面板 vs 文件树），
报冲突是噪声。

## 持久化

用户覆盖存在 **`gui.shortcuts`**（`~/.claude/settings.json`）：

```json
{ "gui": { "shortcuts": { "app.hardRefresh": "mod+shift+r", "layout.toggleLeft": "" } } }
```

- **空字符串 = 显式解绑**（用户清掉了这个键）
- 未出现的 id 用默认表的值
- 上下文型的覆盖**被忽略**（只读）
- 每个实例大小约 30 字符；15 条约 500 字符 —— 对 7KB 的 settings.json 无压力

**多窗口同步免费**：各窗口都监听 `SETTINGS_CHANGED`，改键后自动重载。
分发器**每次按键都读最新配置**（`getSettings().shortcuts`），所以改完立即生效、
不用重启。

## 分发的上下文规则（`shouldDispatch`）

这是"为什么我按快捷键没反应"的唯一源头，规则集中在一处：

| 上下文 | 行为 |
|---|---|
| 普通 | 全部生效 |
| **输入框 / 富文本内** | **单字母无修饰 → 不拦截**（用户在打字）；带修饰键的组合、功能键（`F1`~`F12`）照常生效 |
| **Monaco 内** | `F1` / `Ctrl+Shift+P` **让给 Monaco** 自己的命令面板（与既有行为一致）；其余带修饰键的组合照常 |

「带修饰键的组合在输入框里也生效」是刻意的：否则用户在输入框里按 `Ctrl+,`
打不开设置，很别扭。

## B（OS 级全局热键）：**只预留结构，未实现**

`ShortcutEntry` 已带两个字段供将来使用：

```ts
scope: "app" | "os"     // 本期只产出 "app"
os?: "win" | "mac"      // 平台限定
```

将来接 Tauri `global-shortcut` 插件时，**筛选 `scope === "os"` 的条目直接注册即可**
（该插件要的正是「键 + 作用域」）。设置面板已经把 `scope === "os"` 的条目渲染成
只读（同上下文型）。

**未实现的原因**：B 服务的是"应用失焦时也能唤出"（如全局热键呼出窗口），
与本期"应用内管理"是不同能力，且需要新增 Rust 插件 + 权限 + 注册逻辑。

## 新增快捷键的流程

1. 想清楚属于哪一类（全局 / 命令型 / 上下文型）
2. 在 `DEFAULT_SHORTCUTS` 里加一条 —— **位置即优先级**（靠前者在冲突中赢）
3. 有 `commandId` 的确认该命令已注册（`commandRegistry.register`）
4. 上下文型必须标 `contextual: true`
5. 加 i18n（`shortcuts.item.<id>`，zh + en 都要）
6. 跑 `shortcuts.test.ts` —— 其中「表本身自洽性」5 条会自动校验 id 唯一、
   无冲突、键位已归一化、scope 合法

## 已知缺口：i18n 键路径没有类型安全

`t(key: string)` 接受**任意字符串** —— 键拼错时 `tsc` 不报错，`t()` 会**原样返回
键名**，于是界面上直接印出 `shortcuts.item.paletteOpen` 这种东西。

**本项目已踩过**：`shortcuts` 块曾被误放进 `settings` 命名空间，而代码读的是顶层
路径，整个快捷键页面显示原始键名；`tsc` 全程干净。

**当前防线**：`src/i18n/shortcutsKeys.test.ts` 用「`t()` 返回值 ≠ 键名本身」+
「zh/en 键集合一致」两条断言覆盖快捷键相关的键。**新加 i18n 键时值得照抄这个模式。**

**根治方案（独立一轮，未做）**：把 `t()` 的 key 参数收窄成字面量联合类型
（由 `zh` 的类型推导）。规模与阻碍：

| 项 | 数量 |
|---|---|
| `t("literal")` 调用点 | ~2,205 |
| **动态拼键**（`` t(`a.${x}`) ``） | ~8 处真实用例 |

**动态拼键是硬阻塞** —— `t(\`guard.status.${status}\`)`、`` t(`toolbar.effort_${l.id}`) ``
无法用字面量联合表达。要类型化就得先把它们改成**映射表**
（`{ on: "guard.status.on", off: "guard.status.off" }`）—— 这是逐个改业务代码，
不是加个类型标注就能完事。故确认为**独立重构**，不混在其他任务里做。
